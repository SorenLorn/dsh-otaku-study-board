# Phase 4A.3：真实 DSH 宿主验收与视觉参数最终校准

## 一、阶段目标

基于当前 `4.0.0-rc.1` 版本，对 Phase 4A.2 的修改进行真实 DSH 宿主验收。

本阶段不是新功能开发，也不是新一轮 UI 重构。

核心目标：

1. 验证 V4 浅色毛玻璃的实际透色效果。
2. 验证 V4 深色 L1/L2 的层次。
3. 验证 V3 经典模式 PieChart 空态。
4. 验证 1440、1100、720 三档宽度。
5. 验证页面滚动、视图切换、弹窗层级和控制台错误。
6. 只有发现明确问题时，才进行最小范围修复。

## 二、严格保护范围

以下内容禁止修改：

- 不进入 Phase 4B。
- 不增加统计卡微可视化。
- 不统一 V3/V4 按钮。
- 不修改 V3 深色 Add 按钮。
- 不修改 V3 任务行图标。
- 不修改 V3 默认浅色视觉。
- 不修改业务逻辑、数据结构、存储和统计口径。
- 不修改已经确定的页面结构。
- 不随意调整 1180/720 断点。
- 不增加依赖。
- 不修改 package、manifest、宿主 API。

本阶段原则：能通过验收就冻结，不为了追求主观上的完美而反复修改。

## 三、真实宿主验收

必须在实际 DSH CLI 0.1.1-rc.2 环境中测试当前插件。

不能只通过 jsdom、静态 CSS 审查或 Playwright 模拟结果宣称宿主验收通过。

### A. V4 浅色模式

检查：

- 背景渐变是否延伸至 Dashboard 内容区中部。
- L1 卡片是否能够自然透出背后的玫瑰色、雾紫色。
- 卡片是否仍然具有奶油白玻璃质感。
- 标题、数字、辅助文字是否清晰。
- Hero 标题是否受到中部渐变影响。
- 是否出现背景颜色过重、卡片发灰或视觉脏乱。

当前参数：

- L1：rgba(255,253,250,.52)
- L2：rgba(255,253,250,.40)

### B. V4 深色模式

检查：

- L1 是否明显区别于 L2。
- 两种玻璃表面是否有自然的明度差。
- 边框是否足够克制。
- 阴影是否自然。
- 文字、数字、辅助信息是否清晰。
- 是否出现整块卡片过暗或层次消失。

当前参数：

- L1：rgba(46,39,49,.66)
- L2：rgba(48,41,52,.44)
- L1 边框透明度：.10
- L2 边框透明度：.06

### C. V3 经典模式

检查：

- 默认浅色视觉是否与 4A.2 修改前一致。
- Hero、ProjectBar、五张统计卡、任务区、按钮没有意外变化。
- 「当日会话构成」没有数据时不再显示空圆环。
- 空态文字在卡片中垂直位置自然。
- 有数据时圆环仍正常显示。

注意：V3 深色 Add 和任务行图标问题只记录，不修复。

## 四、响应式测试

分别在以下视口宽度测试：

| 宽度     | 检查内容                          |
| ------ | ----------------------------- |
| 1440px | Dashboard 双列、统计卡四列、页面整体比例     |
| 1100px | 断点附近卡片宽度、Hero、ProjectBar、筛选控件 |
| 720px  | 单列布局、统计卡双列、按钮和输入框是否挤压         |

每个宽度检查：

1. 页面是否出现水平滚动条。
2. 卡片是否超出父容器。
3. 文本是否被截断。
4. 按钮是否发生挤压。
5. ProjectBar 是否溢出。
6. 是否出现不合理的大面积空白。

使用浏览器控制台执行：

```
({
  scrollWidth: document.documentElement.scrollWidth,
  clientWidth: document.documentElement.clientWidth,
  overflow: document.documentElement.scrollWidth >
            document.documentElement.clientWidth
})
```

请记录每档宽度的实际结果，不允许只写「正常」。

## 五、交互与运行检查

至少验证：

1. V3/V4 视图切换时是否出现首帧闪白。
2. V4 页面滚动时背景是否连续。
3. 打开确认弹窗时，弹窗是否能够正确覆盖通知条。
4. 关闭弹窗后页面是否恢复正常。
5. 浅色与深色切换后，页面是否正确更新。
6. 控制台是否出现新增 JS 错误。
7. 是否存在明显滚动卡顿。

backdrop-filter 性能：  
如果没有可用 FPS 数据，不得填写「性能正常」。  
应标记为未测量，并说明实际观察到的情况。

## 六、修复规则

验收发现问题后：

1. 先提供问题证据。
2. 说明问题产生的原因。
3. 判断是否属于 Phase 4A 范围。
4. 只修改必要的 CSS 或组件代码。
5. 不允许顺手重构其他组件。
6. 每项修改后重新执行相关测试。

如果视觉参数已经合适，不要为了追求更强的玻璃效果继续降低透明度。

如果 `.52` 导致文字对比度不足，可以回退到 `.55`，但必须说明截图证据。

如果深色层次不足，可以微调 L1/L2，但必须同时保证文字可读性。

## 七、代码门禁

如有代码修改，执行：

- tsc --noEmit
- smoke tests
- React component tests
- register-check
- production build

确认 V3 保护范围没有被破坏。

区分：

- 必须修复的问题。
- 可以延期的问题。
- 不属于本阶段的问题。

### 6. 最终结论

只能从以下三个结论中选择：

A. Phase 4A 全部验收通过，可以冻结并进入 Phase 4B。

B. Phase 4A 基本通过，但仍有明确问题，需要小范围修复后复验。

C. Phase 4A 未通过，需要继续排查。

**完成报告后立即停止，不要自行启动 Phase 4B。**
